# Detection Engineering Metrics

Detection rules should be evaluated based on their ability to identify meaningful
security activity while maintaining an acceptable operational workload.

This document defines the core metrics used to evaluate detection effectiveness
within the Parking Smart Enterprise Security Platform.

## 1. True Positive (TP)

A True Positive occurs when a detection generates an alert for activity that is
confirmed to be malicious or represents the intended suspicious behaviour.

Example:

A password-spray detection identifies repeated authentication failures from an
attacker-controlled IP address targeting multiple user accounts.

## 2. False Positive (FP)

A False Positive occurs when a detection generates an alert for legitimate
activity.

Examples include:

- vulnerability scanners;
- approved administrative activity;
- CI/CD automation;
- penetration testing;
- legitimate authentication failures;
- expected infrastructure deployments.

False positives increase investigation workload and can contribute to alert fatigue.

## 3. False Negative (FN)

A False Negative occurs when malicious activity happens but the detection fails
to identify it.

Examples include:

- an attacker remaining below a configured threshold;
- activity occurring outside the detection time window;
- missing telemetry;
- an attacker changing techniques;
- overly broad exclusions introduced during tuning.

False negatives are particularly important when tuning detections because reducing
false positives should not create unacceptable detection gaps.

## 4. Precision

Precision measures how many generated alerts represent relevant or malicious
activity.

Formula:

Precision = TP / (TP + FP)

Example:

If a detection produces:

TP = 8
FP = 2

Precision = 8 / (8 + 2)

Precision = 0.80 or 80%

Higher precision generally means analysts spend less time investigating irrelevant
alerts.

## 5. Recall

Recall measures how much of the known malicious activity was successfully detected.

Formula:

Recall = TP / (TP + FN)

Example:

If:

TP = 8
FN = 2

Recall = 8 / (8 + 2)

Recall = 0.80 or 80%

A detection can have high precision but poor recall if it only identifies a small
subset of malicious activity.

## 6. Precision and Recall Trade-off

Detection tuning must consider both precision and recall.

For example, increasing a password-spray threshold may reduce false positives:

5 failed attempts → 10 failed attempts

However, an attacker performing only eight attempts may no longer be detected.

Therefore:

Higher threshold
    ↓
Potentially fewer false positives
    ↓
Potentially lower detection coverage

Detection tuning should not optimise one metric without considering its impact on
the other.

## 7. Alert Volume

Alert volume measures the number of alerts generated by a detection over a defined
period.

Examples:

- alerts per hour;
- alerts per day;
- alerts per week.

Unexpected increases may indicate:

- attacker activity;
- environmental changes;
- application changes;
- telemetry changes;
- poorly tuned detection logic.

High alert volume alone does not prove that a detection is ineffective.

## 8. Detection Latency

Detection latency measures the time between suspicious activity occurring and the
detection generating an alert.

Detection Latency =
Alert Generation Time - Malicious Activity Time

Lower latency is generally desirable for high-impact threats where rapid containment
is important.

## 9. Mean Time to Detect (MTTD)

MTTD measures the average amount of time required to detect security activity.

MTTD =
Total Detection Time / Number of Detected Incidents

MTTD can help determine whether detection rules and processing pipelines identify
threats quickly enough to support effective response.

## 10. Investigation Workload

Detection quality should also consider the operational effort required to investigate
alerts.

Useful measurements include:

- average investigation time per alert;
- number of alerts requiring manual review;
- repeated alerts for the same underlying activity;
- number of alerts automatically enriched;
- number of alerts automatically resolved or contained.

A detection with reasonable technical accuracy may still require improvement if it
creates excessive analyst workload.

## 11. Rule Execution Health

A production detection should also be monitored for operational health.

Important indicators include:

- successful query execution;
- query failures;
- missing telemetry;
- unexpected schema changes;
- execution duration;
- data ingestion delay;
- rule disabled state.

A detection that does not generate alerts cannot automatically be assumed to be
healthy.

## 12. Detection Quality Example

Consider a password-spray detection over a review period.

Results:

True Positives: 12
False Positives: 3
False Negatives: 2
Total Alerts: 15

Precision:

12 / (12 + 3) = 80%

Recall:

12 / (12 + 2) = 85.7%

These measurements can then be combined with investigation time, alert volume and
detection latency to determine whether further tuning is required.

## 13. Metrics Are Decision Support

No individual metric should determine whether a detection is considered effective.

For example:

- high precision does not guarantee good coverage;
- low alert volume does not mean a rule is effective;
- high alert volume does not necessarily mean a rule is bad;
- zero alerts may indicate missing telemetry rather than absence of attacks.

Metrics should support engineering decisions alongside threat intelligence,
investigation findings, threat hunting and knowledge of the environment.

## 14. Continuous Measurement

Detection performance should be reviewed throughout the detection lifecycle.

Detection
    ↓
Deploy
    ↓
Observe
    ↓
Measure
    ↓
Identify TP / FP / FN
    ↓
Tune
    ↓
Regression Test
    ↓
Redeploy
    ↓
Measure Again

The objective is continuous improvement in detection quality, coverage and
operational efficiency.
